# Field Shift — команда з чотирьох людей

Актуальний склад: **Назар, Влад, Єгор, Олексій**. Сергій більше не учасник. Гілка `data` є історичною: **не видаляти**, доки не перевірено, що її зміни перенесено.

## Власники коду

| Учасник | Гілка | Папки / файли | Результат |
| --- | --- | --- | --- |
| Назар | `data` (агрологіка), інтеграція через PR у `main` | `data/`, `packages/logic/`, `shared/`, `docs/`, кореневі конфіги, `wrangler.jsonc` | Наукова база, оцінювання культур, сівозміна, сезонність, API-контракт, тести й реліз |
| Влад | `ui` | `apps/web/src/` **крім** `map/`; `apps/web/index.html` | Головний екран, введення історії, результати, простий/науковий режими, переклади |
| Єгор | `backend` | `apps/api/` | NASA POWER, джерела ґрунту, межі полів, кеш, API |
| Олексій | `map` | `apps/web/src/map/`, `apps/web/public/` (тільки картографічні ресурси за узгодженням) | Карта світу, шари NASA GIBS, вибір поля, межі, візуалізація |

**Назар — інтегратор**, але теж повноцінний розробник: він забирає агрологіку Сергія та відповідає за її наукову перевірку. Не працювати напряму у `main`: зміни через Pull Request, перевірку та review. Історичну `data` використовує Назар після синхронізації з `main`; попередні коміти не видаляти.

## Інтерфейси між модулями (не міняти самостійно)

- `shared/types.ts`, `shared/validate.ts`, `docs/api-contract.md`: змінює лише Назар **після обговорення** з усіма, хто споживає API.
- `GET /api/crops`, `GET /api/field?lat=&lon=`, `POST /api/analyze`: Єгор реалізує, Влад і Олексій використовують через `apps/web/src/api.ts` (власник Влад).
- `recommend(input: LogicInput): LogicOutput`: Назар реалізує; Єгор викликає, не копіює правила в бекенд.
- `<FieldMap field={...} analysis={...} onMapClick={...} lang={...} />`: Олексій експортує, Влад вставляє. **Не перейменовувати пропси без узгодження.**
- `data/crops.json`: Назар підтримує незмінні `id`; Єгор віддає їх через `/api/crops`.
- `apps/web/package.json` та `package-lock.json`: спільні залежності, **змінює тільки Назар під час інтеграції**, або за погодженням у окремому PR. Інші розробники пишуть у PR, яка залежність потрібна.
- Усі тексти для користувача — у `apps/web/src/i18n/` (Влад) або у відповіді API відповідною мовою.

## Що вважати даними NASA

NASA — основне джерело **клімату й супутникових шарів**, а не глобальний кадастр усіх полів. Межі полів дозволено отримувати з **Fields of the World** та **OpenStreetMap**; властивості ґрунту — **ISRIC SoilGrids**; вимоги культур — **FAO EcoCrop**. У кожній відповіді показувати походження даних, дату/період, впевненість і обмеження. Не називати FTW, OSM, SoilGrids чи FAO даними NASA.

Невідомі значення — `null` / «немає даних», не вигадані цифри. Порада не є прогнозом урожайності, фінансовим прогнозом чи гарантією.

## Продукт: мінімальний завершений сценарій

1. Фермер відкриває карту світу й знаходить місце (супутниковий шар, пошук або ручне наближення).
2. Клацає на межі поля, якщо вони доступні. Якщо немає — вибирає точку; не блокуємо аналіз.
3. Вказує **три останні завершені сезони/роки**: головна культура та необов'язкова друга; «не знаю» і «пар» дозволені.
4. Натискає «Аналіз»: API збирає клімат і ґрунт, Назарова логіка оцінює придатність і сівозміну.
5. Бачить прості рекомендації, культури з ризиками, орієнтовні сезони (тільки коли підтверджені даними), три стратегії сівозміни.
6. Натискає «Докладніше»: числові фактори, джерела, припущення та рівень впевненості.

**Точні дати посіву не вигадувати:** потрібні місцеві умови, ризик заморозків, сорт і прогрів ґрунту. Поки перевірено лише кліматичну придатність — писати «орієнтовний сезон» або «потрібна місцева перевірка».

## Робочий процес для новачків

1. Відкрити власну гілку (`data`, `ui`, `backend`, `map`), не `main`.
2. Перед роботою: `git fetch origin` та `git merge origin/main` **у своїй гілці**. Якщо конфлікт — не вгадувати, звернутися до Назара.
3. Редагувати лише свої файли. Зміни спільного контракту спочатку погодити з Назаром.
4. Локально: `npm install`, `npm run check`. Якщо перевірка не пройшла — виправити або описати помилку в PR.
5. `git add <свої файли>`, `git commit -m "feat: короткий опис"`, `git push origin <своя гілка>`.
6. Створити **Draft Pull Request** у `main`; описати що зроблено, як перевірити, які зовнішні джерела використано.
7. Назар перевіряє конфлікти, запускає `npm run check`, погоджує інтеграцію з автором і лише тоді зливає PR.
8. Після кожного merge всі оновлюють свої гілки з `main`.

## Порядок інтеграції

Назар (агрологіка/контракт) → Єгор (API) → Олексій (карта) → Влад (UI). Після **кожного** PR — `npm run check` і тест одного наскрізного сценарію. Порядок може змінитися, якщо зміни вже інтегровані; не перезаписувати новіші файли старими.

## Важливе про існуючий PR карти

Не зливати стару версію `map` автоматично: у `main` вже є новіша інтегрована карта з FTW. Спочатку порівняти файли, зберегти новішу функціональність, тоді оновити PR або закрити застарілий.
